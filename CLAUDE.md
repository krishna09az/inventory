@AGENTS.md

## Project

"Inventory" — a simple offline inventory manager built on Expo SDK 57 (React Native 0.86, React 19, TypeScript strict, Expo Router, React Compiler enabled via `app.json` `experiments.reactCompiler`). It runs in Expo Go; every native module used (`expo-sqlite`, etc.) is bundled there, so keep it that way unless a dev build is intended.

## Commands

Beyond the commands in AGENTS.md:

```bash
npx expo start --tunnel                     # what we use to load on a physical phone (see below); web is at http://localhost:8081
npx expo export --platform android --platform ios --output-dir <tmp dir>   # full bundle check without a device
```

There is no test runner configured. Verification = `npx tsc --noEmit` + `npx expo lint` + `npx expo-doctor`, and an `expo export` when changing imports/config. To sanity-check SQL or a migration without a device, run it against an in-memory `node:sqlite` `DatabaseSync` (Node ≥ 22).

Do **not** run `npm run reset-project` (it's the starter template's script): it moves `src/` and `scripts/` out of the way and replaces the app with a blank one.

## Environment notes (Windows dev machine)

- Shell is Windows PowerShell 5.1. Node/Git were installed via winget; a shell started before that may lack them on PATH. If `npx` isn't found, refresh PATH in the same command: `$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')`.
- A dev server from an earlier session is often still running on port 8081; non-interactive `expo start` then exits ("Use port 8082 instead?"). Check the owner with `Get-NetTCPConnection -LocalPort 8081`. Reuse it for code changes (Fast Refresh picks them up), but restart it after changing `metro.config.js` or `app.json`.
- The Wi‑Fi network is classified as Public and Windows Firewall blocks inbound Node.js on Public, so LAN mode (`expo start` without `--tunnel`) is unreachable from a phone. Tunnel mode uses `@expo/ngrok`, installed as a **project devDependency** because the CLI failed to resolve the global install.
- When `expo start` runs non-interactively it prints no QR code or URL; the tunnel URL is available from ngrok's local API at `http://127.0.0.1:4040/api/tunnels` (use `exp://<host>` in Expo Go).
- `expo-env.d.ts` is gitignored and regenerated by `expo start`; it must exist for `tsc` to pass (it provides the `*.css` / `*.module.css` module types).

## Website (EAS Hosting)

- Production: https://kraftbling-inventory.expo.app (dev domain `kraftbling-inventory`). Deploy = `npx expo export --platform web` then `npx eas-cli@latest deploy --prod --non-interactive`. The export bakes in `EXPO_PUBLIC_*` from `.env.local` (local export, unlike EAS Build).
- Works without COOP/COEP headers (`crossOriginIsolated` is false) because the app only uses async expo-sqlite APIs. EAS Hosting serves `.wasm` as `application/wasm` and falls back to `index.html` for deep links.
- `detectSessionInUrl` is on for web only, so Supabase email-confirmation links (Site URL = the production URL) sign the user straight in.
- To check a web build without the browser extension, drive headless Chrome over the DevTools protocol (Node's global `WebSocket`) and read console errors plus `document.body.innerText`. The sign-in screen rendering means SQLite initialised, since `SQLiteProvider` gates rendering on `migrateDbIfNeeded`.

## Web (browser testing)

expo-sqlite on web is alpha and needs specific config:
- `metro.config.js` adds `wasm` to `assetExts` and sets COEP/COOP headers via `server.enhanceMiddleware` (per the Expo SQLite docs).
- `app.json` uses `web.output: "single"`. `"static"` breaks: server-side rendering fails with `Worker chunk not found for: …expo-sqlite/web/worker.ts`.
- The dev server's HTML response does not actually get the COEP/COOP headers, so `SharedArrayBuffer` is unavailable. Only the **async** expo-sqlite APIs work on web; never use the `*Sync` variants.
- Browser data (OPFS) is separate from the phone's database.

## Architecture

- `src/app/_layout.tsx` — root: `ThemeProvider` → `SQLiteProvider` (`inventory.db`, `onInit={migrateDbIfNeeded}`) → `AuthProvider` → `SyncProvider` → a `Stack` split by `Stack.Protected` on whether there's a Supabase session. Five routes — that's the cap (simplicity is a product goal; don't add screens, use `Alert`s / inline UI instead):
  - `src/app/login.tsx` — email + password sign in / create account (only route when signed out). Shows a setup message if the Supabase env vars are missing.
  - `src/app/index.tsx` — the inventory list (stats, search, low-stock filter, stock count per row, sync status line, “Account” header button → Alert with Sync now / Sign out). Tapping a row opens the product page.
  - `src/app/product.tsx` — product page (`id` param): In / Out / Left totals, avg. purchase price, “Stock in” / “Stock out” buttons, and the dated history of entries.
  - `src/app/item.tsx` — add/edit product modal. Add vs. edit is decided by the optional `id` search param. On add it also takes an opening quantity + price (creates the first inbound entry). The screen loads the row, then renders an inner form component whose `useState` initializers take the loaded values (avoids setState-in-effect, which the React Compiler lint rule rejects).
  - `src/app/movement.tsx` — stock in/out modal (`itemId`, `type`, optional `id` to edit). Inbound: qty, price/unit, date, supplier. Outbound: qty, date, client name, city. Refuses saves/deletes that would make stock negative.
- `src/db/inventory.ts` — the local data layer: `Item` / `Movement` types, schema migrations keyed on `PRAGMA user_version` (bump `DATABASE_VERSION` and add a `currentVersion === N` step for schema changes; never edit earlier steps), and all query helpers. Screens get the DB with `useSQLiteContext()` and pass it into these functions rather than writing SQL inline.
  - Stock is **derived**: `Item.quantity` = Σ inbound − Σ outbound over non-deleted `movements`. The v2 migration turned v1 `items.quantity` into “Opening stock” entries; v3 rebuilt both tables for sync.
  - Sync columns (v3): ids are UUID strings (`expo-crypto` `randomUUID`), `deleted` is a soft delete (every read must filter `deleted = 0`), `dirty = 1` means not yet uploaded. **Every write helper must set `dirty = 1`, bump `updatedAt`, and call `notifyLocalChange()`** — that's what triggers upload.
- Cloud sync (local-first; screens never call Supabase for data):
  - `src/db/sync.ts` — `syncOnce` pushes dirty rows (items before movements, FK), marks them clean only if `updatedAt` is unchanged, then pulls rows with server `updated_at` > `meta.pulledUntil` (minus a 30 s overlap) and upserts them locally unless the local row is dirty. Last write to the server wins. `prepareLocalDataForUser` adopts unowned local data or wipes another account's cache; `clearLocalData` runs on sign-out.
  - `src/providers/sync-provider.tsx` — runs sync on sign-in, app foreground, and 1 s after local changes; exposes `state` / `pending` / `error` and a `dataVersion` counter that screens put in their `useFocusEffect` refresh deps so pulled changes appear.
  - `src/providers/auth-provider.tsx` — session from `supabase.auth.onAuthStateChange`. `src/lib/supabase.ts` — client per the Expo guide (session in `expo-sqlite/localStorage`, auto-refresh only in foreground).
  - `supabase/migrations/` — server schema (snake_case columns; `sync.ts` maps to the local camelCase), `updated_at` set by trigger, owner-only RLS (`user_id` defaults to `auth.uid()`). Change it with a **new** migration (`supabase migration new <name>`; never edit an applied one), then `supabase db push --dry-run` and `supabase db push`. Ship server changes alongside the matching local SQLite migration.
  - Env: `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in `.env.local` (git-ignored; template in `.env.example`); restart the dev server after changing them.
  - To test sync logic without a device, load `src/db/*.ts` in Node with `--experimental-strip-types`-style loading, a `node:sqlite` wrapper exposing the expo-sqlite async methods, a stub for `expo-crypto`, and a fake Supabase client.
  - Movement dates are stored as `YYYY-MM-DD` text, typed as `DD/MM/YYYY` in forms. Formatting/parsing helpers (dates, ₹ with Indian grouping, counts, prices) live in `src/utils/format.ts`; the shared text input is `src/components/form-field.tsx`.
- Theming: colors live in `Colors` in `src/constants/theme.ts` (light/dark pairs, including app-specific `tint`, `warning`, `danger`, `success` — inbound entries are green `success`, outbound use `warning`); read them with `useTheme()` and use `ThemedText` / `ThemedView`. Spacing uses the `Spacing` scale from the same file.
- Platform-specific files use the `.web.ts(x)` suffix (e.g. `use-color-scheme.web.ts`, which uses `useSyncExternalStore` to return `'light'` until hydrated; a leftover from the template's static web rendering, harmless with `"single"` output).
- Lint (`eslint-config-expo`) includes React Compiler rules such as `react-hooks/set-state-in-effect`; prefer derived values, state initializers, or `useSyncExternalStore` over setting state in effects.
